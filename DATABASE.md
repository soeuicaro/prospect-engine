# Database

Postgres via Supabase. Migrations live in `supabase/migrations/`, applied in filename order (`0001_core.sql` → `0008_seed_reference.sql`). See `DEPLOYMENT.md` for how to apply them.

## Multi-tenancy & RLS

Every tenant-scoped table has a `workspace_id` column. `is_workspace_member(ws_id)` (SECURITY DEFINER, defined in `0001_core.sql`) is the single source of truth RLS policies call — it avoids infinite recursion when `workspace_members` itself has RLS enabled. The bulk of tables share one uniform policy generated by a `DO $$ ... $$` loop in `0007_rls.sql`; child tables without a direct `workspace_id` column (`sequence_steps`, `import_errors`, `automation_logs`) scope through their parent via `EXISTS`.

**No table is reachable by the browser without going through this.** The service-role client (`lib/supabase/admin.ts`) bypasses RLS entirely and must only ever run server-side — see `SECURITY.md`.

## Company size: three distinct concepts (never conflated)

Per the product spec, "how big is this company" is deliberately split into three fields on `companies`, each with its own confidence semantics:

1. **`official_size`** (jsonb: `{value, source, source_date, confidence}`) — only ever populated from an actual registry (e.g. Receita Federal `porte`). Never inferred.
2. **`estimated_size`** + `estimated_size_confidence` — a computed operational-scale estimate (`MICRO_LOCAL` / `PEQUENA` / `MEDIA` / `GRANDE_REGIONAL`), always shown as an estimate, never asserted as fact.
3. **Prospect/opportunity score** (`company_scores.opportunity_level`) — commercial potential for *this agency specifically*, not a statement about the company's objective size or revenue.

## Data confidence & source traceability

Nothing enrichment-derived is stored without `confidence` (`HIGH`/`MEDIUM`/`LOW`) and a row in `company_sources` (`source_type`, `source_name`, `collected_at`, `confidence`). `company_score_factors` keeps the evidence trail behind every point in the Prospect Score ("Why this lead?").

## Storage economy

Deliberately **not** stored: raw HTML from crawled websites, images, large PDFs. `company_analysis` keeps flags/metadata/a content hash, never a full page dump — see PROMPT MASTER §85, §137, §233. This matters concretely on Supabase's free tier (see `FREE_PLAN.md`).

## Indexing

Indexes exist only where a query in `lib/queries/*` actually filters/sorts by that column: `companies(workspace_id)`, `companies(workspace_id, state, city)`, `companies(workspace_id, cnpj)`, trigram indexes on `trade_name`/`legal_name` (search), `companies(workspace_id, pipeline_stage_id)`, `companies(workspace_id, industry_id)`, GIN on `tags`, `company_scores(workspace_id, prospect_score desc)` (Top Leads), plus due-date partial indexes on `followups`/`tasks` for the "today's queue" views. Not indexed on principle: anything without a caller — see PROMPT MASTER §131.

## Soft delete / archive

`companies.deleted_at` (excluded from every query by default) and `companies.archived_at` (excluded from active lists, kept for history) are separate — a deleted company is gone from the UI; an archived one is just deprioritized. Both are reversible only via direct database access in V1 (no "restore" UI yet).

## Idempotency

`imports.idempotency_key` (unique per workspace) plus per-row dedup evaluation (`lib/domain/dedup.ts`, EXACT/LIKELY/POSSIBLE/NO match on CNPJ, website domain, phone, email, name+city) means re-running the same import file does not create duplicate companies — matches never auto-merge; EXACT/LIKELY matches are skipped, POSSIBLE matches are left for manual review (never silently dropped).

## Demo data

`0008_seed_reference.sql` seeds **real, non-fake** reference data (CNAE codes, starter industry taxonomy) shared by every workspace. No synthetic company/contact records are seeded into the schema — a dedicated demo-data script is documented as a roadmap item rather than shipped with fabricated personal-looking data by default.
